PHASE 1 : SOCLE UNIFIÉ "DATA ASSET" & ASSET REGISTRY
================================================================================
Objectif : Poser les structures de données fondamentales, le schéma d'URI universel,
les métadonnées déterministes, et le registre centralisé d'Assets par session.

- [✅] 1.1 Modèle de base `DataAsset` & `AssetMetadata` (`core/discovery/data_asset.py`) :
      - Identifiant unique & URI (`scheme://path` ou `data_type://target`)
      - Métadonnées techniques déterministes : taille (bytes/chars), tokens estimés,
        hash SHA-256, mime_type, encoding, line_count
      - Déclaration des `capabilities` supportées (ex: `['search', 'read_slice', 'get_head', 'get_tail', 'schema', 'summarize']`)
      - Système de prévisualisation déterministe (`preview`) sans appel LLM
      - Méthode abstraite/générique `dump_data()`, `get_head()`, `get_tail()`, `read_slice()`
- [✅] 1.2 Registre Universel `AssetRegistry` (`core/discovery/asset_registry.py`) :
      - Gestion du cycle de vie des assets par session (`session_id`)
      - Indexation et résolution rapide par URI (`resolve_asset(uri)`)
      - Stockage immuable des contenus bruts en mémoire/disque local de session
      - Génération du Manifeste global pour l'Orchestrateur
- [✅] 1.3 Validation & Tests unitaires du Socle Phase 1

================================================================================
PHASE 2 : INGESTION INTELLIGENTE & CLASSIFICATION VOLUMÉTRIQUE (INPUT INGESTOR)
================================================================================
Objectif : Remplacer l'injection aveugle du message utilisateur par un pipeline
d'ingestion déterministe ultra-rapide.

- [✅] 2.1 Moteur `InputIngestor` (`core/discovery/input_ingestor.py`) :
      - Politiques de volumétrie configurables (`INLINE_LIMIT`, `SOFT_ASSET_LIMIT`, `HARD_ASSET_LIMIT`)
      - Classification instantanée : `INLINE` vs `ASSET`
      - Gestion transparente des pièces jointes (fichiers glissés-déposés, logs, documents)
- [✅] 2.2 Classes d'Assets Spécialisées :
      - `UserPayloadDataAsset` (`inputs://turn_N/payload`)
      - `FileDataAsset` (`files://filename.ext`)
- [✅] 2.3 Intégration dans le flux d'entrée de l'Orchestrateur & SessionMemory (Enregistrement effectif de FilesProvider, InputsProvider, FilesExplorer et ingestion automatique)
- [✅] 2.4 Validation & Tests d'ingestion (messages géants, fichiers attachés, messages courts)

PHASE 5 : GROS RETOURS D'OUTILS, INTERPOLATION DES VARIABLES & PROTECTION DES LLMS PROFONDS
================================================================================
Objectif : Éviter que les sorties d'outils massives, les variables volumineuses ($@_)
ou les interpolations ne saturent l'arbre d'exécution, le ToolsManager, ou les LLMs profonds.

- [✅] 5.1 Modèle `ToolOutputDataAsset` (`core/discovery/data_asset.py` ou `tool_output_asset.py`) :
      - URI format : `outputs://step_{step_id}_{tool_name}`
      - Stockage immuable du retour brut intégral (stdout, stderr, dump JSON, logs)
      - Calcul déterministe en O(1) de l'AssetMetadata (taille, lignes, tokens, aperçu head/tail)
      - Enregistrement automatique dans l'AssetRegistry de session

- [✅] 5.2 Interception & Stockage dans `Executor` (`core/executor.py`) :
      - Détection de volumétrie à la fin de chaque étape d'exécution d'outil :
        * Si retour <= `INLINE_LIMIT` (~3 000 chars) : stocké directement dans le registre de variables.
        * Si retour > `INLINE_LIMIT` : encapsulé dans un `ToolOutputDataAsset`. La variable dans le registre
          stocke la référence URI, les métadonnées et un aperçu compact.
      - Sécurisation de l'évaluation de convergence sémantique (`_evaluate_semantic_convergence`) :
        reçoit uniquement l'aperçu synthétique de l'Asset, évitant l'explosion du juge LLM.

- [✅] 5.3 Sécurisation de l'Interpolation des Variables (`_interpolate_text` & `_handle_abstract_task`) :
      - Protection des sous-tâches abstraites : si une variable `$@_` volumineuse est interpolée
        dans le prompt d'un Solver enfant (`step_context`, `goal`), injection de la référence URI
        et du manifeste de l'Asset plutôt que 50 Mo de texte brut.
      - Le Solver enfant explore la donnée via le `DiscoveryEngine` (`outputs://...`).

- [✅] 5.4 Protection du `ToolsManager` & des Outils Internes d'Analyse (`tools/tools_manager.py` & `tools/internal_tools.py`) :
      - Le premier LLM de décision voit déjà les métadonnées (`$@_name` : type + desc).
      - Sécurisation des handlers profonds (`llm_analyze_data`, `extract_json_value`) :
        protection contre le débordement de tokens avec budget maximal garanti et drill-down sans saturation de prompt.

- [✅] 5.5 Intégration du Provider `outputs://` dans `Orchestrator` et `FilesExplorer` :
      - Enregistrement effectif de `OutputsProvider` et mapping dans `FilesExplorer` pour le forage des résultats d'outils.

- [✅] 5.6 Validation & Tests d'exécution avec gros retours d'outils (stdout massif, JSON géant).
